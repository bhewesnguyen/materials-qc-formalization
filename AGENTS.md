# Agent operating instructions

These rules govern implementation in the proposed `formal-science` project. Follow the user's current instructions if they change scope. Documentation and code comments use no em dashes.

## Work boundary

- One mathematical milestone is active at a time. Stage 0 is complete and audited (audits/stage0/v1/). The finite dissipator algebra assignment in NEXT_FABLE_TASK.md is implemented in this snapshot and its handoff is deliverables/dissipator/v1/HANDOFF.md; it awaits its independent audit. No further milestone is active until that audit selects one. TURNS.md indexes every round.
- Start with the accepted informal theorem contract. Record definitions, quantifiers, assumptions, source, and intended use before implementing a substantial proof.
- Search pinned Mathlib and selected downstream source before introducing a definition or proving a named theorem from scratch.
- Do not silently weaken a conclusion, specialize a universal parameter, change a convention, or add an assumption that packages the desired conclusion. Propose contract changes explicitly in DECISIONS.md.
- Source inspection, successful compilation, accepted axioms, semantic review, and novelty are separate statuses.
- Do not claim no Lean formalization exists everywhere. State the exact search scope and candidate endpoint.

## Dependencies and design

- Use one compatible Lean/Mathlib toolchain and pin dependency revisions. Commit `lean-toolchain` and `lake-manifest.json` after creating the package.
- Do not run a broad dependency update as a routine proof repair. Test upgrades on a separate branch.
- Choose one quantum representation ecosystem. Avoid importing all surveyed quantum repositories together.
- Prefer existing matrix, PSD, adjoint, finite-sum, and linear-map APIs. Add thin adapters only where needed.
- Preserve license and authorship when copying permitted source. Record original repository, commit, path, and changes.
- Use finite, explicitly nonempty types where normalization requires them. Name the norm and tensor/basis ordering.
- `H=0`, basis 0/1, and rates `a:0->1`, `b:1->0` are the initial pilot conventions.

## Proof trust

- Release exports may depend only on `propext`, `Classical.choice`, and `Quot.sound`, or a subset.
- Release exports must not depend on `sorryAx`, custom axioms, or native-evaluation axioms. Interpret names according to the pinned Lean version.
- Do not use `sorry`, `admit`, or custom `axiom` declarations in release modules. Keep unfinished sketches in documentation or a clearly excluded work area and never count them as completed proofs.
- Deliberate negative fixtures generated by scripts/test_verify.py are excluded from release modules. Their rejected custom axioms, proof holes, and invalid signatures are validation evidence; do not turn them into accepted release proofs.
- Do not alter compiler checking, validation scripts, notation, or theorem definitions to bypass a failing gate.
- Tactic proof search is fine when it produces an accepted ordinary proof term under the project trust policy.
- Grepping for placeholder words is supplementary; inspect transitive axioms for every public theorem.

## Build coverage and review

- Maintain an authoritative release module/export list. Use an umbrella import or explicit targets so every release theorem is actually compiled.
- Build the target after each small change, then the full release set at the milestone gate.
- Record exact commands, exit codes, commit hashes, compiler output, and transitive axiom output.
- Audit the elaborated type and relevant definitions. A theorem can be axiom-clean yet vacuous, over-assumed, or mathematically misnamed.
- Include a witness that assumptions are satisfiable and meaningful boundary cases. Inspect one zero rate, both zero rates, and equal positive rates when implementing the later rate-dependent pilot; Stage 0 has no rate assumptions.
- A stationary state does not by itself establish convergence or CPTP dynamics. A positive map is not automatically completely positive. A generator is not a channel.
- A specific model does not prove generic GKSL or Perron-Frobenius. Finite lattice theorems do not prove continuum or thermodynamic results.
- Once a validation harness is introduced, verify that it rejects missing release exports and forbidden assumptions. Do not write tests that merely restate implementation internals.

## Task sizing and handoff

- Prefer one lemma or a short dependency-connected group per task.
- If two focused sessions add new prerequisite layers without closing the probe, write a blocker with exact goals and options. Do not expand to unrelated topics.
- At each stage boundary, fill AUDIT_HANDOFF_TEMPLATE.md and stop for the already-planned mathematical audit unless the user has explicitly authorized continuing stages.
- Handoff layout. The milestone key (for example `dissipator`) joins `evidence/<key>/`, `deliverables/<key>/v<k>/`, `audits/<key>/v<k>/`, and the tag `<key>-milestone-v<k>`, where `k` is the round number and increments if an audit sends the milestone back. The completed template lives only at `deliverables/<key>/v<k>/HANDOFF.md`, next to a `POINTER.json`. Reports from the auditor are stored as received under `audits/<key>/v<k>/`. `TURNS.md` records one row per round. Archives are derived from the tag with `git archive` and are never tracked; `SOURCE_MANIFEST.json` covers every tracked file except itself and therefore matches the archive by construction.
- Handoff sequence. Commit, tag, regenerate `SOURCE_MANIFEST.json` before the commit, create the archive from the tag into the ignored `deliverables/<key>/v<k>/` location, verify the archive against the manifest, and stop. The implementer commits; the user pushes. When the audit returns, store it under `audits/`, copy any accepted next assignment into `NEXT_FABLE_TASK.md`, and add the `TURNS.md` row.
- Report failures candidly. Never invent successful builds, exact theorem names, timing benchmarks, or accepted upstream status.
- Keep public claims proportional to evidence. The user must understand and own prospective Mathlib contributions and comply with current AI-disclosure policies.

## Out of scope for the initial release

General circuit DSLs, purification and entropy frameworks, a GUI, multiple solver backends, continuum electronic structure, infinite Fock space, full generic GKSL reproving, and simultaneous OR implementation.
